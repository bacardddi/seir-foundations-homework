Paragraph (minimum 5 sentences):
A database is a structured system for storing and retrieving information so
applications can reliably save data, search through it, and update it without
losing integrity — which is why everything from banking systems to social
networks depends on one. Relational databases organize information into fixed
tables made of rows and columns, while non-relational databases use flexible
formats like key-value pairs, documents, or graphs that scale more easily
across distributed servers. In AWS, relational engines are provided through
Amazon RDS and Aurora, whereas DynamoDB serves as the main NoSQL key-value
option. PostgreSQL is widely trusted because it's open source, stable, and
feature-rich, though it can require more tuning and operational expertise
compared to a fully managed NoSQL service. Balerica uses SQLite in the
teaching lab because it's just a single file with no server to configure,
which keeps the exercises simple. A real bank, however, needs a system
designed for heavy concurrency, strict security, backups, and high
availability — requirements that SQLite isn't built to handle.

Numbers + sources:
- Relational model introduced in 1970 - E. F. Codd, "A Relational Model of Data for Large Shared Data Banks", 1970
- PostgreSQL is the most used database among professional developers - Stack Overflow Developer Survey, 2024
- Amazon DynamoDB launched in 2012 - AWS announcement, 2012

One thing the AI said that I double-checked, and what I found:
The AI said the V in PIC 9(10)V99 shows where the decimal point goes but the

Paragraph (minimum 5 sentences):
When I worked through the lab, I finally started to understand why COBOL is
still such a big deal in banking. COBOL was created back in 1959, and it was
meant to read almost like English so business people could follow the logic.
In the Balerica lab, I actually saw this myself. The account_lookup and
payment_post programs are written in COBOL, and they use the same
return-code style that real mainframes use: 0 for success, 4 for not found,
8 for a business rule rejection, and 12 for an environment problem. Seeing
those codes show up in my runs made the system feel a lot more "real."

I also learned how COBOL stores money. The ledger uses a PIC 9(10)V99 field,
which means the decimal point isn't actually stored. So when Alice's balance
shows up as 000000500000, the last two digits are the cents. It felt strange
at first, but now I understand why banks do it — it keeps the math exact.

Numbers + sources:
- COBOL was created in 1959 - Wikipedia: COBOL
- About 95% of ATM swipes rely on COBOL - Reuters, 2017
- About 220 billion lines of COBOL are still in use - Reuters, 2017

Paragraph (minimum 5 sentences):
I asked the AI some questions about SWIFT and how international money
transfers work. One thing that surprised me is learning that SWIFT doesn't
actually move money. It only sends secure messages between banks telling
them what to do. The real money moves through correspondent banks, which
hold accounts with each other. That's why sending money to another country
can go through several banks and take a few days.

Every bank has a SWIFT/BIC code, which is 8 or 11 characters long. It's
kind of like how the Balerica lab uses fixed-format 6-digit account IDs.
SWIFT used to rely mostly on old MT messages, like MT103 for customer
payments, but now it's moving to ISO 20022, which has richer and more
structured data. This connects to the lab because our accounts.dat file
also uses fixed-width fields, and banks are slowly modernizing those kinds
of formats. Seeing how SWIFT works made the lab feel more real to me,
because the same ideas — fixed formats, structured messages, and old
systems being modernized — show up in both places.

Numbers + sources:
- SWIFT was founded in 1973 - Wikipedia: SWIFT
- Over 11,000 institutions in more than 200 countries and territories - Wikipedia: SWIFT
- Around 45 million messages per day on average in recent years - Wikipedia: SWIFT

Paragraph (minimum 5 sentences):
I asked the AI some questions about APIs, REST, GET vs POST, and HTTP status
codes. I learned that an API is just a set of rules that lets one program
talk to another. Most web APIs today use REST, which means you send HTTP
requests to URLs (endpoints) and get back data, usually in JSON.

GET is used to read data, and POST is used to send new data. In the
Balerica lab, the FastAPI server had endpoints like GET /status,
GET /accounts/{id}, and POST /payments, and I could test them all on the
/docs page.

The part that stood out to me is how the API sits on top of the old COBOL
programs. When I call GET /accounts/100001, FastAPI actually runs
account_lookup behind the scenes and turns its return code into an HTTP
status. So a COBOL return code 4 (not found) becomes a 404. That's how banks
give old mainframe systems a modern interface. Seeing how the API layer
works made the lab feel more real to me, because it showed how modern
systems and old COBOL programs can work together.

Numbers + sources:
- HTTP was created by Tim Berners-Lee starting in 1989 - Wikipedia: HTTP
- REST was defined by Roy Fielding in 2000 - Wikipedia: REST
- HTTP status codes are grouped into five classes, from 1xx to 5xx - MDN: HTTP response status codes
